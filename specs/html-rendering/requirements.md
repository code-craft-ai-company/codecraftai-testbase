# HTML Report Templates - Requirements Document

## Introduction

The HTML Report Templates system provides a client-side web application for rendering and displaying test execution results in the TestBase framework. It delivers a single-page application (SPA) architecture using vanilla JavaScript and Web Components, dynamic data loading from JSON/JSOS result files generated by the Result Recording system, modular and reusable UI components for displaying test summaries, configurations, results, and artifacts, specialized tab pages for rendering media artifacts (images, sounds, time series charts), and themeable styling through CSS custom properties for branding customization. The system operates entirely client-side, loading test result data via AJAX requests and rendering it through a component-based architecture.

## Glossary

- **TestSummaryBanner**: A web component that displays the test run summary banner with build information, timestamps, and result metrics
- **TestSummaryConfiguration**: A web component that displays test configuration including command, environment, packages, and landscape information
- **TestSummaryResultDetail**: A web component that displays detailed test results grouped by package or rendered as a tree
- **TestSummaryResultGroup**: A web component that displays a group of test results for a single package with aggregate metrics
- **TestSummaryResultItem**: A web component that displays an individual test result with errors, failures, and tasking information
- **TestSummaryArtifacts**: A web component that displays test artifacts organized in tabs with embedded iframe content
- **TestSummaryImportFailures**: A web component that displays import errors encountered during test discovery
- **TestSummaryFilesAndFolders**: A web component that displays the output directory structure for navigation
- **MojoCollapsible**: A base web component providing collapsible/expandable panel functionality
- **MojoPropertyTable**: A web component for displaying key-value property tables
- **MojoTabSet**: A web component providing tabbed interface functionality
- **Shadow_DOM**: The encapsulated DOM tree attached to web components for style isolation
- **JSOS**: JSON Separated Object Stream format used for streaming test results
- **Catalog_JSON**: A JSON file containing directory contents (files and folders arrays) for navigation
- **CSS_Custom_Properties**: CSS variables defined with @property for theming support
- **Display_Mode**: The rendering mode for results (GROUPED by package or TREE hierarchical)
- **Filter_Mode**: The filtering mode for results (NONE, PASSED, FAILED, ERRORED, SKIPPED)
- **Result_Code**: The outcome status of a test (PASSED, FAILED, ERRORED, SKIPPED, UNKNOWN)

## Requirements

### Requirement 1: Page Entry Point Structure

**User Story:** As a test developer, I want a well-structured HTML entry point, so that the test summary report loads correctly with all required resources.

#### Acceptance Criteria

1. THE testsummary.html page SHALL include script references to all required JavaScript files (testsummary.js, testsummary-components.js, mojo-components.js, icon-components.js, webcomponent-helpers.js, testsummary-helpers.js, prism.js)
2. THE testsummary.html page SHALL include stylesheet references to all required CSS files (branding-theme.css, testsummary.css, mojo-components.css, icon-styles.css, prism.css)
3. THE testsummary.html page SHALL define a section-header containing the testsummary-banner component
4. THE testsummary.html page SHALL define a section-body containing testsummary-configuration, testsummary-resultdetail, testsummary-artifacts, and testsummary-importfailures components
5. THE testsummary.html page SHALL define a section-footer containing the testsummary-filesandfolders component
6. WHEN the page loads, THE System SHALL call on_page_load to register components and refresh the page

### Requirement 2: Web Component Registration

**User Story:** As a framework developer, I want web components to be properly registered, so that custom elements can be used in the HTML templates.

#### Acceptance Criteria

1. THE register_testsummary_components function SHALL register all TestSummary web components with customElements.define
2. THE register_mojo_components function SHALL register all Mojo base web components with customElements.define
3. EACH web component class SHALL define a static tagname property for registration
4. EACH web component class SHALL define a static template property containing the HTML template
5. THE component registration SHALL occur before any component elements are created or accessed

### Requirement 3: Shadow DOM Encapsulation

**User Story:** As a framework developer, I want web components to use Shadow DOM, so that component styles are encapsulated and do not leak to the parent document.

#### Acceptance Criteria

1. EACH web component constructor SHALL call attachShadow with mode 'open'
2. EACH web component constructor SHALL set shadowRoot.innerHTML to the component template
3. EACH web component constructor SHALL call addGlobalStylesToShadowRoot to adopt global styles
4. THE addGlobalStylesToShadowRoot function SHALL copy document stylesheets to the shadow root's adoptedStyleSheets
5. THE getGlobalStyleSheets function SHALL cache the global stylesheets for reuse across components

### Requirement 4: Test Summary Banner Display

**User Story:** As a test developer, I want to see a summary banner with key test run information, so that I can quickly understand the test run status.

#### Acceptance Criteria

1. THE TestSummaryBanner component SHALL display the automation pod name from the summary data
2. THE TestSummaryBanner component SHALL display the branch, build, and flavor from build information
3. THE TestSummaryBanner component SHALL display the start and stop timestamps
4. THE TestSummaryBanner component SHALL display the overall result status (PASSED/FAILED)
5. THE TestSummaryBanner component SHALL display metrics for errors, failed, skipped, passed, and total counts
6. THE TestSummaryBanner component SHALL calculate and display a pass score percentage
7. WHEN calculating the score, THE System SHALL use the formula (passed / (total - skipped)) * 100

### Requirement 5: Configuration Display

**User Story:** As a test developer, I want to see the test configuration, so that I can understand the test environment and settings.

#### Acceptance Criteria

1. THE TestSummaryConfiguration component SHALL display the command used to run the tests
2. THE TestSummaryConfiguration component SHALL display environment variables in a collapsible property table
3. THE TestSummaryConfiguration component SHALL display installed packages in a collapsible property table
4. THE TestSummaryConfiguration component SHALL display landscape configuration in a collapsible section
5. WHEN configuration data is unavailable, THE System SHALL hide the corresponding section
6. THE landscape section SHALL display device groups, data profiles, and services when available

### Requirement 6: Landscape Configuration Display

**User Story:** As a test developer, I want to see the landscape configuration details, so that I can understand the test environment topology.

#### Acceptance Criteria

1. THE TestSummaryConfigurationLandscape component SHALL display device groups with their devices
2. THE TestSummaryDeviceGroup component SHALL display the group name and list of devices
3. THE TestSummaryDeviceObject component SHALL display device properties (name, deviceType, host, role, credentials, features, skip)
4. THE TestSummaryServiceObject component SHALL display service properties (name, serviceType, host, credentials)
5. THE TestSummaryDataProfileObject component SHALL display data profile properties (name, profileType, host, credentials)
6. WHEN a landscape section has no data, THE System SHALL hide that section

### Requirement 7: Result Detail Display

**User Story:** As a test developer, I want to see detailed test results, so that I can analyze individual test outcomes.

#### Acceptance Criteria

1. THE TestSummaryResultDetail component SHALL support rendering results grouped by package
2. THE TestSummaryResultDetail component SHALL support rendering results as a hierarchical tree
3. WHEN rendering by package, THE System SHALL create TestSummaryResultGroup components for each package
4. THE TestSummaryResultGroup component SHALL display the package name and aggregate metrics (errors, failures, skipped, passed)
5. THE TestSummaryResultGroup component SHALL contain TestSummaryResultItem components for each test
6. THE TestSummaryResultItem component SHALL display test name, start time, and result status

### Requirement 8: Test Result Item Display

**User Story:** As a test developer, I want to see individual test details, so that I can understand why tests passed or failed.

#### Acceptance Criteria

1. THE TestSummaryResultItem component SHALL display the test name with moniker suffixes if present
2. THE TestSummaryResultItem component SHALL display the test start timestamp
3. THE TestSummaryResultItem component SHALL display error count with color-error styling when errors exist
4. THE TestSummaryResultItem component SHALL display failure count with color-fail styling when failures exist
5. THE TestSummaryResultItem component SHALL display skip indicator with color-skip styling when skipped
6. THE TestSummaryResultItem component SHALL display pass indicator with color-pass styling when passed
7. THE TestSummaryResultItem component SHALL be expandable to show detailed error and failure information

### Requirement 9: Error and Failure Display

**User Story:** As a test developer, I want to see error and failure details, so that I can diagnose test issues.

#### Acceptance Criteria

1. THE TestSummaryErrorsCollapsible component SHALL display a collapsible list of errors
2. THE TestSummaryFailuresCollapsible component SHALL display a collapsible list of failures
3. THE TestSummaryExceptionTrace component SHALL display exception type, arguments, and traceback lines
4. THE traceback display SHALL format each trace line with file path, line number, and code context
5. THE code context SHALL use Prism.js for syntax highlighting
6. WHEN errors or failures are empty, THE System SHALL hide the corresponding collapsible section

### Requirement 10: Tasking Group Display

**User Story:** As a test developer, I want to see tasking results within tests, so that I can analyze distributed task execution.

#### Acceptance Criteria

1. THE TestSummaryTaskGroup component SHALL display tasking group name and aggregate metrics
2. THE TestSummaryTaskGroup component SHALL contain TestSummaryTaskResult components for each tasking
3. THE TestSummaryTaskResult component SHALL display tasking name, worker, and result status
4. THE TestSummaryTaskResult component SHALL display prefix and return value when available
5. THE tasking group SHALL track passed, failed, and errored counts for its taskings

### Requirement 11: Import Failure Display

**User Story:** As a test developer, I want to see import failures, so that I can fix test discovery issues.

#### Acceptance Criteria

1. THE TestSummaryImportFailures component SHALL display a list of import errors from import_errors.jsos
2. THE TestSummaryImportFailureItem component SHALL display the module path that failed to import
3. THE TestSummaryImportFailureTrace component SHALL display the import error traceback
4. WHEN no import errors exist, THE System SHALL hide the import failures section
5. THE import failure display SHALL be collapsible for each error item

### Requirement 12: Artifacts Display

**User Story:** As a test developer, I want to see test artifacts, so that I can review generated files and media.

#### Acceptance Criteria

1. THE TestSummaryArtifacts component SHALL load the artifacts/catalog.json file
2. THE TestSummaryArtifacts component SHALL create tabs for each artifact folder containing a tab.html file
3. EACH artifact tab SHALL embed the tab.html file in an iframe
4. THE artifact tabs SHALL use MojoTabSet for tab navigation
5. WHEN no artifacts folder exists, THE System SHALL hide the artifacts section

### Requirement 13: Files and Folders Navigation

**User Story:** As a test developer, I want to navigate the output directory, so that I can access generated files.

#### Acceptance Criteria

1. THE TestSummaryFilesAndFolders component SHALL display files from the catalog.json
2. THE TestSummaryFilesAndFolders component SHALL display folders from the catalog.json
3. EACH file entry SHALL be a clickable link to open the file
4. EACH folder entry SHALL be a clickable link to navigate to the folder
5. THE component SHALL be displayed in the page footer section

### Requirement 14: Data Loading from JSON

**User Story:** As a framework developer, I want to load test data from JSON files, so that the report can display test results.

#### Acceptance Criteria

1. THE fetch_json function SHALL load and parse JSON files via AJAX fetch
2. THE fetch_json function SHALL return null and log an error when the file cannot be loaded
3. THE load_summary function SHALL load testrun_summary.json into g_summary
4. THE load_configuration function SHALL load landscape-declared.json and startup-configuration.json
5. THE load_catalog function SHALL load catalog.json into g_catalog
6. THE load_artifact_folders function SHALL load artifacts/catalog.json and sub-folder catalogs

### Requirement 15: Data Loading from JSOS Stream

**User Story:** As a framework developer, I want to load streaming results from JSOS files, so that large result sets can be processed efficiently.

#### Acceptance Criteria

1. THE fetch_json_stream function SHALL load and parse JSOS (JSON Separated Object Stream) files
2. THE JSOS parser SHALL split the file content by record separator and parse each JSON object
3. THE load_results_from_stream function SHALL load testrun_results_stream.jsos
4. THE load_import_errors function SHALL load import_errors.jsos
5. THE stream loading SHALL handle empty files gracefully

### Requirement 16: Result Processing and Grouping

**User Story:** As a framework developer, I want results processed and grouped, so that they can be displayed in organized views.

#### Acceptance Criteria

1. WHEN display mode is GROUPED, THE System SHALL organize results by package name
2. THE split_test_fullname function SHALL extract package_name and test_name from the full test name
3. THE finalize_test_result_item function SHALL categorize results and update counters
4. THE result processing SHALL track parent-child relationships for tests, tasking groups, and taskings
5. THE result processing SHALL accumulate passed, failed, errored, and skipped counts
6. WHEN filter mode is not NONE, THE System SHALL filter results by the specified status

### Requirement 17: Collapsible Panel Functionality

**User Story:** As a test developer, I want collapsible panels, so that I can expand and collapse sections to manage screen space.

#### Acceptance Criteria

1. THE MojoCollapsible component SHALL provide a clickable button to toggle content visibility
2. THE toggle function SHALL switch content display between visible and hidden
3. THE MojoCollapsible component SHALL update the icon content (+/-) based on expanded state
4. THE MojoCollapsibleLvl2 and MojoCollapsibleLvl3 components SHALL provide nested collapsible levels
5. THE syncData method SHALL accept header text, content element, and initial expanded state

### Requirement 18: Tab Set Functionality

**User Story:** As a test developer, I want tabbed interfaces, so that I can switch between different views.

#### Acceptance Criteria

1. THE MojoTabSet component SHALL display tab buttons for each registered page
2. THE MojoTabSet component SHALL track the currently selected tab
3. THE tabClick function SHALL switch to the clicked tab and update visual selection
4. THE switchToSelected function SHALL show the selected tab content and hide others
5. THE MojoTabPage component SHALL provide tab button and content container elements

### Requirement 19: Property Display Components

**User Story:** As a test developer, I want property display components, so that key-value data is presented clearly.

#### Acceptance Criteria

1. THE MojoPropertySingle component SHALL display a single label-value pair
2. THE MojoPropertySingle component SHALL provide a copy button to copy the value to clipboard
3. THE MojoPropertyTable component SHALL display multiple properties in a grid layout
4. THE MojoPropertyTable component SHALL create label and value elements for each property
5. THE copyValue function SHALL copy the property value to the clipboard when clicked

### Requirement 20: CSS Theming Support

**User Story:** As a test developer, I want customizable theming, so that reports can be branded for different organizations.

#### Acceptance Criteria

1. THE branding-theme.css file SHALL define CSS custom properties for result colors (error, fail, pass, skip, warn, ghost)
2. THE branding-theme.css file SHALL define CSS custom properties for background colors
3. THE branding-theme.css file SHALL define CSS custom properties for banner colors and section header colors
4. THE branding-theme.css file SHALL define a CSS custom property for the logo image URL
5. THE color classes (color-error, color-fail, color-pass, color-skip, color-warn, color-ghost) SHALL apply the corresponding custom property colors

### Requirement 21: Result Color Coding

**User Story:** As a test developer, I want color-coded results, so that I can quickly identify test outcomes.

#### Acceptance Criteria

1. THE System SHALL apply color-error (maroon) styling to errored test counts and indicators
2. THE System SHALL apply color-fail (red) styling to failed test counts and indicators
3. THE System SHALL apply color-pass (green) styling to passed test counts and indicators
4. THE System SHALL apply color-skip (gray) styling to skipped test counts and indicators
5. THE System SHALL apply color-ghost styling to zero counts for visual de-emphasis
6. THE color styling SHALL be applied via CSS classes that reference custom properties

### Requirement 22: Images Tab Page

**User Story:** As a test developer, I want to view image artifacts, so that I can review screenshots and visual outputs.

#### Acceptance Criteria

1. THE tab-images.html page SHALL load image files with png and jpg extensions from the catalog
2. THE page SHALL display each image with its filename as a header
3. THE images SHALL be displayed in a flex container layout
4. THE fetch_items function SHALL filter catalog files by the specified extensions
5. THE page SHALL handle missing or empty catalogs gracefully

### Requirement 23: Sounds Tab Page

**User Story:** As a test developer, I want to play audio artifacts, so that I can review sound outputs.

#### Acceptance Criteria

1. THE tab-sounds.html page SHALL load audio files with mp3 and wav extensions from the catalog
2. THE page SHALL display each audio file with its filename as a header
3. THE page SHALL provide HTML5 audio elements with playback controls
4. THE audio elements SHALL be displayed in a flex container layout
5. THE page SHALL handle missing or empty catalogs gracefully

### Requirement 24: Time Series Tab Page

**User Story:** As a test developer, I want to view time series charts, so that I can analyze temporal data.

#### Acceptance Criteria

1. THE tab-timeseries.html page SHALL load chart configuration from chartsummary.json
2. THE page SHALL load time series data from JSOS files specified in the configuration
3. THE page SHALL render charts using D3.js library
4. THE charts SHALL display time on the X-axis and values on the Y-axis
5. THE charts SHALL support multiple series with color coding
6. THE page SHALL handle missing or empty data gracefully

### Requirement 25: Syntax Highlighting

**User Story:** As a test developer, I want syntax-highlighted code in tracebacks, so that code context is readable.

#### Acceptance Criteria

1. THE System SHALL include Prism.js library for syntax highlighting
2. THE System SHALL include prism.css stylesheet for highlighting styles
3. THE traceback code context SHALL be wrapped in appropriate Prism markup
4. THE Prism.highlightAll function SHALL be called after results are rendered
5. THE Prism configuration SHALL use manual mode to control highlighting timing

### Requirement 26: Error Handling for Data Loading

**User Story:** As a framework developer, I want graceful error handling, so that missing data does not break the report.

#### Acceptance Criteria

1. WHEN a JSON file fails to load, THE System SHALL catch the error and log a message
2. WHEN a JSON file fails to load, THE System SHALL continue loading other data sources
3. WHEN configuration data is missing, THE System SHALL hide the corresponding UI section
4. WHEN artifact catalog is missing, THE System SHALL skip artifact loading
5. THE error handling SHALL NOT cause the page to fail or display error messages to users

### Requirement 27: Page Refresh Orchestration

**User Story:** As a framework developer, I want coordinated page refresh, so that all sections load and display correctly.

#### Acceptance Criteria

1. THE refresh_page function SHALL orchestrate loading and refreshing all page sections
2. THE refresh_page function SHALL load summary, configuration, results, import errors, and catalog in parallel
3. EACH load function SHALL trigger its corresponding refresh function upon completion
4. THE artifact loading SHALL only occur if the artifacts folder exists in the catalog
5. THE Prism syntax highlighting SHALL be triggered after results are rendered

### Requirement 28: Entity Escaping

**User Story:** As a framework developer, I want HTML entity escaping, so that special characters in test data are displayed safely.

#### Acceptance Criteria

1. THE entity_escape function SHALL replace ampersand (&) with &amp;
2. THE entity_escape function SHALL replace less-than (<) with &lt;
3. THE entity_escape function SHALL replace greater-than (>) with &gt;
4. THE entity escaping SHALL be applied to user-provided content before rendering
5. THE escaping SHALL prevent XSS vulnerabilities from test data content

### Requirement 29: Time Formatting

**User Story:** As a test developer, I want formatted timestamps, so that test timing is easy to read.

#### Acceptance Criteria

1. THE get_time_difference function SHALL calculate the duration between start and stop times
2. THE time formatting SHALL display hours, minutes, and seconds as appropriate
3. THE timestamps SHALL be displayed in a consistent format across all components
4. THE banner SHALL display start and stop times from the summary data
5. THE result items SHALL display their start timestamps

### Requirement 30: Clipboard Copy Functionality

**User Story:** As a test developer, I want to copy values to clipboard, so that I can easily use test data elsewhere.

#### Acceptance Criteria

1. THE MojoPropertySingle component SHALL provide a copy button next to the value
2. THE copyValue function SHALL use navigator.clipboard.writeText to copy the value
3. THE copy button SHALL provide visual feedback when clicked
4. THE clipboard functionality SHALL work within Shadow DOM components
5. THE copy functionality SHALL handle text content from various element types
